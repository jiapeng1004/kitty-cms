## ADDED Requirements

### Requirement: 主数据提交成功后必须投递 Kafka 以驱动 ES
在资源**主数据**及影响**可检索**字段的**持久化事务**（或经架构评审认可的等价边界）**成功提交之后**，系统 **MUST** 向**约定**的 **Kafka Topic** 发送一条（或多条在文档中明确定义合并策略的）**资源变更**消息。消息**用于**由 **MAM 方** 异步**消费**并**写回/更新** **Elasticsearch**；该路径与 `material-search-sync` 的「**事务后异步、最终一致**」目标一致，且本变更将**投递通道**明确定义为 **Kafka**。

#### Scenario: 新建资源并入库成功
- **WHEN** 新资源在 DB 中提交成功
- **THEN** 在事务提交后**可观测**地产生一条（或经合并策略的）Kafka 消息，**不得**在事务未提交前对外发送**最终**同步意图（避免与 DB 回滚竞态）

#### Scenario: 仅更新可检索编目
- **WHEN** 仅可检索字段/编目变更并提交
- **THEN** 同样 MUST 产生对应消息，使 ES **最终**与 DB 可检索部分一致

### Requirement: 必须由 MAM 自消费并写 ES
系统 MUST 由 **MAM 服务进程**或**明确归属的 MAM 工兵组件** 订阅上述 Topic 并**执行** ES 写入/更新/删除，**不**将「写 ES」仅交给无归属的旁路服务而不定义 SLA（若采用独立进程，MUST 在部署文档中写清**归属**与**监控**）。消费者 **MUST** 具备**幂等**与**可重试**能力。

#### Scenario: 重复投递不破坏最终文档
- **WHEN** 同一资源变更消息**重复**到达
- **THEN** 多次处理后的 **ES 文档**终态**一致**（以资源 id 与内容版本/时间戳为幂等键）

#### Scenario: 暂时故障后可恢复
- **WHEN** 消费者因 ES 或网络暂时不可用而失败
- **THEN** 消息按配置重试，重试后系统**最终**达到一致状态；**可选** 死信与告警（在实现/运维层定义）

### Requirement: 消息内容须足以支撑全量/增量建索引
Kafka 消息体 **MUST** 至少包含 `resourceId`、变更**类型/意图**（全量/部分字段），以及**版本或时间戳**之一供消费者做幂等；**SHOULD** 包含足够重建 ES 文档的**关键字段**或**版本指针**，以避免消费者必须再查 DB 才能写完整文档（**若**消费者策略为**仅 id + 重查 DB**，实现 MUST 在 design 的「待实现定稿项」中锁死，并注意 DB 与 ES 之间的一致性窗口）。

#### Scenario: 消费者可根据消息更新 ES
- **WHEN** 某条消息被正常消费
- **THEN** ES 中可检索到与该资源在 DB 中**一致**的（可检索子集）内容，允许**合理延迟**

### Requirement: 与双队列/旧实现并存时须收敛为单一事实来源
若代码库中仍存在**非 Kafka** 的**同类**资源索引投递实现，在落地阶段 **MUST** 收敛为**一种**对 ES 的**事实**投递与消费链，**避免**双写、重复全量、乱序无治理；在收敛完成前，**MUST** 有明确迁移计划，且本 spec 以 **Kafka + MAM 自消费** 为**目标态**。

#### Scenario: 仅一条投递路径在运行期生效
- **WHEN** 某次资源提交成功
- **THEN** 对 ES 的**效果**在逻辑上**只应**经目标链触发一次**有效**的索引工作流（以幂等可吸收重复，但**不**以重复为常态）

### Requirement: 资源从检索中移除时 ES 须最终一致
当资源在业务上**不再**应被全文/聚合检索时（**硬删除**、**进入不可检索的终态**等，以**领域**定义为准），系统 **MUST** 投递**可被消费者识别**的删除或** tombstone 语义**消息，使 ES 中的对应文档在**合理延迟**内**被删除或不可命中**；**不得**长期保留「DB 已删/资源已不可见」而 ES 仍可搜到。

#### Scenario: 资源删除
- **WHEN** 资源在 DB 中完成删除或标记为**不可被检索**且产品规定不出现在检索结果
- **THEN** 消费者处理消息后，以该资源 id 在 ES 中**查询/召回**的**应然**行为与**产品**一致（一般为**无**或**重定向/提示已删除**）

### Requirement: 消息顺序与乱序
若同一 `resourceId` 在短时间内产生多条消息，消费者 **MUST** 以**版本号或时间戳**较**新**的为准处理**终态**（**last-write-wins** 或等价规则），**不得**在乱序时让旧状态覆盖**较新**的 DB/业务事实。实现 MAY 依赖**重查 DB** 作为权威。

#### Scenario: 先收到新后收到旧
- **WHEN** Kafka 分区重平衡或网络导致**后到的**消息时间更早
- **THEN** 最终 ES 文档与 DB **一致**，**不**以「先到先写」**牺牲**新事实
