## Context

本变更面向 MAM（媒资管理）场景，对现有 material 服务进行经典 DDD 重建。当前状态是包结构已存在，但业务能力尚未成型，且历史
`material-func` 实现不满足以下硬约束：分层纯净、分布式一致性、异构多存储、栏目权限强语义、编目版本化、任务中心化、检索与向量化协同。

该设计以“DB 为中心，ES 为边缘”为核心原则，要求在不牺牲可扩展性的前提下先完成可运行闭环，并确保后续可替换基础设施实现（如队列、存储、用户中心、转码平台）。

关键约束来自业务原文与 proposal：

- 统一 REST 风格：成功返回干净 DTO，异常返回专用异常 DTO。
- `exchange` 层承载 API 入参与出参定义，兼容 RPC 风格调用。
- 公共语义强约束：公共记录使用 `public`，无父节点固定 `parentId=0`，不使用 `null` 表示同类语义。
- 无“上帝用户”绕过：`public=false` 的强制权限禁用对管理员同样生效。
- 个人栏目根采用虚拟根/占位符策略（`pri_` 命名空间）。
- 分片上传通过请求头传递区间信息，必须处理并发冲突与幂等。
- 事务后异步同步 ES，并支持向量多来源并存。

涉及主要干系方：内容运营、审核人员、平台管理员、上层三方接入方（S3 轻量接入）、平台基础设施维护者（用户中心、转码服务、配置中心）。

## Goals / Non-Goals

**Goals:**

- 建立 material 的 DDD 分层基线：`api(exchange)/application/domain/infra/repo` 职责清晰，注解不越层污染。
- 建立完整资源中心领域：栏目、资源、编目、权限、任务、转码策略、消息与审核流程具备统一模型。
- 建立异构存储体系：S3 与磁盘可并存，按存储记录路由，支持分片上传并发控制。
- 建立分布式运行能力：锁、缓存、队列、配置中心、用户上下文均走领域接口 + infra 适配。
- 建立检索与向量能力：DB 主查询，ES 做全文/向量增强；MySQL 与 ES 同时保存向量，支持多来源共存。
- 建立可迁移基础：历史实现可平滑下线，新能力可逐步替换原流程引擎/外部平台绑定方式。

**Non-Goals:**

- 本阶段不实现完整流程引擎编排，仅预留策略绑定扩展点。
- 本阶段不做编目历史归档压缩与冷热分层，仅保证永久保留与可查询。
- 本阶段不引入 Kafka 等新中间件作为默认实现，先以 Redisson 队列/锁落地。
- 本阶段不定义前端最终交互细节（UI 布局、复杂拖拽体验），仅提供稳定后端契约。
- 本阶段不提供跨租户复杂隔离模型，默认在现有用户与权限域内运行。

## Decisions

### 1) 分层与模块边界：强 DDD + 反腐适配

**决策**

- `domain` 只包含聚合、值对象、领域服务、领域事件与仓储/网关接口，不使用 MyBatis Plus、Swagger、Validation 注解。
- `repo` 层实体允许 MyBatis Plus 注解，负责 ORM 映射与持久化细节。
- `api(exchange)` 层定义请求/响应 DTO 与 controller 注解，`application` 层负责编排用例与事务边界。
- 用户中心、配置中心、转码平台、对象存储、队列、缓存、分布式锁均通过 `domain` 或 `application` 定义端口接口，由 `infra` 适配。

**理由**

- 避免历史实现里“框架模型入侵领域”的高耦合问题，便于替换基础设施实现。

**备选方案**

- 方案A：直接在领域对象叠加 ORM/Validation 注解。  
  放弃原因：短期开发快，但长期演进成本高，且违反你的明确约束。

### 2) API 契约：干净 DTO + 专用异常 DTO

**决策**

- 成功响应不使用统一外层泛型包装；错误响应统一映射为专用异常 DTO（含错误码、国际化消息、trace 信息）。
- `messageSource` 作为错误文案与提示文案统一来源，异常处理对齐现有全局异常风格。
- `exchange` 层对象作为 controller 与 RPC 风格入口的共享契约载体。

**理由**

- 降低前端与三方接入方解析复杂度；保证异常语义稳定、可国际化。

**备选方案**

- 方案A：统一 `Result<T>` 风格。  
  放弃原因：与当前硬性要求冲突，且会增加跨端处理分支。

### 3) 栏目树与权限语义：虚拟根 + public 强语义

**决策**

- 栏目分“普通栏目”和“个人栏目”。
- 个人栏目根为虚拟根：逻辑标识 `pri_用户id`，可在树接口中显式返回，但不要求栏目表中存在同 id 实体。
- 个人子栏目可使用 `parent_id=pri_用户id` 进行挂载；资源在个人根内使用 `catalog_id=pri_用户id` 表达命名空间。
- 虚拟根不可排序；其子节点可排序；个人根下子栏目禁止跨根移动到其他私有根或普通栏目。
- 栏目权限采用三态记录语义：
    - `roleId + catalogId + permissionCode + true`：角色具备权限
    - `public + catalogId + permissionCode + true`：全体具备权限
    - `public + catalogId + permissionCode + false`：全体禁止且不可勾选（管理员不可绕过）
- 树与权限查询结果走缓存，变更时精确失效。

**理由**

- 满足“无上帝用户”和个人素材库的业务需求，同时保证树查询与权限判断性能。

**备选方案**

- 方案A：个人根也落库为真实栏目行。  
  放弃原因：会带来用户生命周期与栏目生命周期强耦合，且不利于轻量创建。

### 4) 资源模型：单主键标识 + 文件夹资源化

**决策**

- 资源表仅使用一个主键 id 作为唯一标识，不引入并行 contentId。
- 资源必须归属栏目（`catalogId` 非空）；不在文件夹中的资源固定 `parentId=0`。
- 资源类型统一枚举：视频、音频、图片、文本、Office、其他、文件夹。
- 文件夹本身也是资源，可递归嵌套并承载目录结构上传映射。

**理由**

- 简化唯一标识体系，降低跨表关联与迁移复杂度。

**备选方案**

- 方案A：双轨标识（id + contentId）。  
  放弃原因：当前阶段收益小于复杂度，且与你的约束不一致。

### 5) 存储体系：异构多存储 + 工厂路由

**决策**

- 将“文件记录”和“存储记录”解耦：文件记录负责业务属性与索引字段；存储记录保存内外网地址、AK/SK、协议类型、bucket/路径等。
- 通过存储工厂根据协议类型（S3/磁盘）与存储实例选择具体驱动。
- 预留 NAS 本地挂载兼容面：磁盘协议实现采用统一对象键语义，避免暴露底层路径细节。
- 构建对外链接时优先从缓存读取存储元数据，缓存 miss 再回源数据库。

**理由**

- 支持多存储并存与后续扩容，避免“全局唯一存储”成为瓶颈。

**备选方案**

- 方案A：单存储全局配置。  
  放弃原因：无法满足异构部署和多业务线隔离需求。

### 6) 分片上传：Header 协议 + 并发安全

**决策**

- 分片核心字段通过请求头传递：`Content-Length`、`Content-Range`（0-based）。
- 应用层维护上传会话（upload session）与分片状态；并发写入时使用“分布式锁 + 幂等检查”组合控制。
- 分片完成校验包含：字节覆盖完整性、指纹一致性（文件大小 + 分段 CRC）。
- 允许同文件秒传/去重依赖指纹索引，但最终落库仍走显式确认流程。

**理由**

- 兼容标准客户端行为，且可跨 Pod 稳定处理并发上传。

**备选方案**

- 方案A：仅靠数据库唯一键防重。  
  放弃原因：无法覆盖分片并发覆盖冲突与乱序提交问题。

### 7) 编目模型：模板绑定独立表 + EAV + 版本双字段

**决策**

- 模板与字段的绑定改为独立绑定表，支持排序与稳定扩展，不再使用逗号串字段。
- 编目实例采用 EAV：`resourceId + templateId + fieldId + value`。
- 版本策略采用 `last + version`：
    - 查询最新：直接 `last=true`
    - 查询历史：按业务版本上界检索 `version<=N`
- 编目版本永久保留，不做归档淘汰。

**理由**

- 在可扩展性、查询性能与存储压力之间取得平衡。

**备选方案**

- 方案A：JSON 大字段存整份编目。  
  放弃原因：字段级检索、权限控制、差异审计能力弱。

### 8) 转码与任务中心：策略优先级 + 轻量任务统一模型

**决策**

- 转码策略抽象为平台化配置：平台标识 + 策略参数；凭据与地址由配置中心读取。
- 栏目可绑定转码策略；资源上传后优先使用栏目策略；同时保留未来流程引擎接管入口。
- 资源任务统一轻量模型：任务记录 id、资源标题、任务类型、三方任务 id、进度、状态。
- 转码失败重试采用逻辑删除历史态并复用业务记录主键，更新外部任务 id（若有）。

**理由**

- 统一任务视图，减少多系统状态对齐成本。

**备选方案**

- 方案A：每类任务一套独立表与接口。  
  放弃原因：接口碎片化严重，不利于资源中心化展示。

### 9) 检索与向量：事务后队列同步，DB 主 ES 边

**决策**

- 资源与编目变更在事务提交后发布领域事件，投递到分布式队列。
- 消费端执行 ES 同步，消息分两类：全量 doc 重建、字段增量 update。
- 向量化默认覆盖音视频图片文本/Office；向量记录包含来源平台标识，允许一个资源多来源并存。
- 提供 `NONE` 向量实现，返回安全空向量以打通非生产链路与降级流程。
- 非全文/非向量查询优先走 DB，避免 ES 成为主依赖。

**理由**

- 保证写路径一致性与读路径可控性，避免“写 ES 失败影响主交易”。

**备选方案**

- 方案A：同步写 ES。  
  放弃原因：主交易链路被外部检索系统可用性牵制。

### 10) 站内信与审核流：领域内建 + 跨 Pod 协调 (ddd适配需要实现在user服务上使用grpc去调用)

**决策**

- 站内信作为独立子域，消息写入 DB 后通过队列广播，SSE 网关按用户会话分发，支持跨 Pod 实时推送。
- 通用审核工作流定义统一状态机（待审/通过/拒绝），并提供查询接口供资源域聚合展示。

**理由**

- 满足实时性与分布式部署要求，同时复用统一队列能力。

**备选方案**

- 方案A：单 Pod 内存推送。  
  放弃原因：多实例部署下消息丢失与不可达风险高。

## Risks / Trade-offs

- [个人虚拟根语义复杂，易出现边界漏洞] → 通过专用领域服务集中处理 `pri_` 规则，并增加跨根移动与排序约束测试。
- [分片上传并发冲突导致状态错乱] → 上传会话加锁 + 幂等 token + 完成态校验三层保护。
- [权限缓存与实时性冲突] → 采用“短 TTL + 精确失效事件”策略，并对关键权限变更走强制失效。
- [ES 异步同步造成短暂不一致] → 明确最终一致性 SLA，提供按资源手动重放同步任务。
- [多向量来源导致存储增长] → 先按来源白名单控制写入，后续引入按来源/时间维度清理策略（不影响本期语义）。
- [无 root 兜底导致运维操作受限] → 提供“原初用户 + 显式权限策略”脚本化初始化与审计日志。
- [异构存储接入复杂度提升] → 用统一存储工厂和协议适配测试套件约束新增驱动质量。

## Migration Plan

1. **模型落地阶段**  
   新建 material 领域模型、repo 实体、exchange DTO 与基础 infra 适配接口，不复用旧业务逻辑。
2. **双轨读写阶段（短期）**  
   新接口先行接入，旧接口只读或逐步下线；通过开关控制流量切换。
3. **数据迁移阶段**  
   完成栏目、资源、编目、权限、任务、存储记录结构迁移；对历史数据补齐 `parentId=0`、`public` 语义字段。
4. **异步链路接入阶段**  
   启用事务后队列、ES 同步、向量写入与重放工具；验证最终一致性指标。
5. **外部系统联调阶段**  
   联调 kitty-user gRPC、kitty-transcoder gRPC、S3 兼容接入与 SSE 推送链路。
6. **灰度与回滚策略**  
   灰度按栏目或租户范围切分；回滚时关闭新写入并回退读路由到旧实现（保留迁移映射与审计日志）。

## Open Questions

- `pri_` 虚拟根在数据库字段类型上的统一方案是否采用字符串主键域，还是“显示字段 + 计算字段”双轨表达？
- 分片上传会话与分片明细是否需要独立表，还是可由对象存储元数据 + 缓存状态组合实现？
- `public=false` 的权限禁用粒度是否需要区分 API 级与操作级（如下载原文件、导出编目）？
- 站内信 SSE 的离线补偿策略是否需要默认实现（未在线用户的未读追赶）？
- 向量化平台来源标识是否需要全局注册中心（避免来源 code 冲突）？
- S3 兼容 starter 的认证模式是否仅 AK/SK，还是预留临时凭证（STS）接口？
